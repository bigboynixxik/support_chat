# Support Chat Microservice

Данный репозиторий содержит микросервис чата поддержки для платформы MurPlace, написанный на языке Go.
Архитектура построена на базе паттерна Publish-Subscribe (In-Memory Hub) и взаимодействует с основным монолитом (Django) посредством протокола gRPC для аутентификации пользователей.

## Окружение и Зависимости
Для корректной работы микросервиса необходимо наличие конфигурационного файла .env в корневой директории:

```Go
APP_ENV=dev                      # dev, local или prod (влияет на уровень логирования)
HTTP_PORT=8082                   # Внутренний порт микросервиса
AUTH_GRPC_TARGET=backend:50051   # Адрес gRPC сервера основного монолита
```
## Архитектура взаимодействия (WebSocket)

Протокол взаимодействия строится поверх установленного WebSocket-соединения. Точка подключения: ws://<domain>/ws/support.

    1. Аутентификация (Gatekeeper)
    В целях безопасности передача токена в Query-параметрах не используется. Аутентификация происходит посредством отправки первого кадра (Auth Frame).

    ### Поведение системы:

    Клиент устанавливает TCP-соединение.

    Система выделяет клиенту 5 секунд на прохождение аутентификации (Read Deadline).

    Клиент обязан отправить JSON с JWT-токеном.

    Сервер производит синхронный gRPC-запрос к монолиту. При успешном ответе таймаут на чтение снимается, сокет переходит в режим дуплексного обмена сообщениями.

    Auth Frame (от клиента):

    ```JSON
    {
    "action": "auth",
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6..."
    }
    ```
    Ответ об успешной авторизации (от сервера):

    ```JSON
    {
    "action": "system",
    "status": "authenticated"
    }
    ```
    2. Маршрутизация сообщений
    Обмен сообщениями производится в формате JSON. Бизнес-логика опирается на ролевую модель, полученную от gRPC-сервиса (RoleClient, RoleOperator).

    #### Контракт сообщения:

    ```JSON
    {
    "action": "send_message",
    "text": "Текст сообщения",
    "target_id": 0
    }
    ```
    ### Правила обработки поля target_id (int64):

    При отправке от лица RoleClient: поле target_id игнорируется (рекомендуется передавать 0). Система автоматически доставляет сообщение всем активным соединениям с ролью RoleOperator.

    При отправке от лица RoleOperator: поле target_id строго обязательно. Оно должно содержать уникальный идентификатор клиента (ID из базы данных). Система произведет целевую доставку сообщения указанному клиенту.

    3. Отказоустойчивость и Управление соединениями
    Heartbeat (Ping/Pong): Сервер инициализирует отправку управляющих Ping кадров каждые 54 секунды. Время ожидания ответа составляет 60 секунд. При отсутствии Pong ответа от браузера клиента TCP-соединение принудительно разрывается для предотвращения утечек памяти.

    Graceful Shutdown: При получении системных сигналов SIGINT или SIGTERM, приложение корректно завершает работу HTTP-сервера, предотвращая потерю обрабатываемых данных.

    Изоляция потоков: Чтение и запись в сокет разнесены в независимые горутины (ReadPump, WritePump). Конкурентный доступ к пулу соединений управляется центральным диспетчером (Hub) через каналы, исключая состояния гонки (Race Conditions).

    4. Обработка ошибок
    В случае критических нарушений контракта (неверный токен, истекший срок действия, невалидный JSON), микросервис отправляет сообщение с описанием ошибки и завершает соединение кодом статуса 1000 (Normal Closure).

    Формат ошибки:

    ```JSON
    {
    "error": "invalid auth frame"
    }
    ```
